## Findings

### Critical

**1. Out-of-bounds loop causes a guaranteed TypeError crash**
- **Severity**: Critical
- **Confidence**: 100
- **File**: `src/user.js:4-5`
- **Issue**: The loop condition is `i <= users.length`. On the final iteration `i === users.length`, so `users[i]` is `undefined`, and `users[i].id` throws `TypeError: Cannot read properties of undefined (reading 'id')`. This fires on every call where the id is not matched earlier (including any lookup that should return `null`), and even on an empty array. The `return null` on line 9 is effectively unreachable — the function throws instead of returning `null` for a not-found user.
- **Fix**: Use `i < users.length`.

**2. SQL injection via string concatenation**
- **Severity**: Critical
- **Confidence**: 95
- **File**: `src/user.js:12-13`
- **Issue**: `buildUserQuery` interpolates `name` directly into the SQL string: `"SELECT * FROM users WHERE name = '" + name + "'"`. Any caller-supplied value (e.g. `x'; DROP TABLE users; --`) is injected verbatim — a classic SQL injection. This also breaks on legitimate input containing an apostrophe.
- **Fix**: Return a parameterized query (placeholder + params array), e.g. `{ text: "SELECT * FROM users WHERE name = $1", values: [name] }`, and let the driver handle escaping. Never build SQL by concatenation.

### Important

**3. Loose equality (`==`) for id comparison**
- **Severity**: Important
- **Confidence**: 80
- **File**: `src/user.js:5`
- **Issue**: `users[i].id == id` uses loose equality, which coerces types — `1 == "1"` is `true`, `0 == ""`/`0 == false` is `true`, `null == undefined` is `true`. This can return the wrong user or a false positive. It is also inconsistent with the type-strict convention in `src/math.js`, which strictly validates types (`typeof a !== 'number'`, `src/math.js:5`).
- **Fix**: Use strict equality `===`.

**4. Missing input validation, inconsistent with project convention**
- **Severity**: Important
- **Confidence**: 78
- **File**: `src/user.js:3-9`
- **Issue**: `src/math.js` establishes a clear convention of guarding inputs and throwing `TypeError` on bad arguments (`assertNumbers`, `src/math.js:3-9`). `findUser` performs no validation: a non-array `users`, or an array containing a `null`/`undefined`/primitive element, causes an uncaught `TypeError` at `users[i].id` (line 5) rather than a controlled failure or skip. For consistency with the codebase's error-handling style, invalid arguments should be validated explicitly.
- **Fix**: Validate `Array.isArray(users)` (throw `TypeError` like `math.js` does) and guard each element (e.g. `if (users[i] && users[i].id === id)`), matching the defensive style of `assertNumbers`.
